# Google (Calendar + Gmail + Docs + Sheets) — setup protocol

OAuth клиент уже установлен на сервере. НЕ проси пользователя создавать
OAuth client, скачивать JSON или что-то настраивать в Google Cloud Console.
От пользователя нужны только ДВЕ вещи: email и redirect URL после авторизации.

## Шаг 1 — Проверка (Discovery)

Запусти через bash_exec:

```bash
gog auth list 2>/dev/null || true
```

Если показывает аккаунт с gmail и calendar:
- Проверь: `gog calendar list --account <email>`
- Если работает — скажи пользователю: "Google подключён, аккаунт <email>."
- Если токен протух — переходи к Шагу 2.
- Вызови `link_google_account` с email.

Если аккаунтов нет — переходи к Шагу 2.

## Шаг 2 — Спроси email

Спроси у пользователя: "Какой Gmail подключаем?"

Дождись ответа с email. Это ВСЕГДА собственный email клиента.

## Шаг 3 — Авторизация (remote flow)

### ⚠ ЖЕЛЕЗНЫЕ ПРАВИЛА ПОТОКА (иначе авторизация зацикливается)

Эти правила нарушались и приводили к бесконечному циклу «последний раз» +
ошибке `Missing code verifier`. Соблюдай строго:

1. **URL генерирует ТОЛЬКО `gog ... --step 1`.** НИКОГДА не собирай ссылку
   `https://accounts.google.com/o/oauth2/auth?...` руками. Саморобный URL не имеет
   PKCE `code_verifier`, который gog сохранил у себя → `--step 2` обломается.
2. **НИКОГДА не создавай и не редактируй файлы `oauth-manual-state-*.json` вручную.**
   В них лежит секрет PKCE (`code_verifier`), создать его умеет только `gog --step 1`.
   Подделка state-файла = гарантированный `Missing code verifier`.
3. **Шаг 1 и Шаг 2 — один непрерывный поток с ОДИНАКОВЫМИ root-флагами**
   (`--services gmail,calendar,docs,sheets,drive --redirect-host social.eightgate.ai`).
4. **Пока ждёшь код от пользователя — НЕ запускай Шаг 1 повторно.** Каждый новый
   Шаг 1 создаёт новый state и убивает `code_verifier` предыдущего. Если пользователь
   долго не отвечает и надо начать заново — запусти Шаг 1 СНОВА и пришли НОВУЮ
   ссылку (старая уже мертва), и заверши Шаг 2 сразу.
5. **Один клиент, один redirect:** клиент `849429310357-...` +
   `https://social.eightgate.ai/oauth2/callback`. НИКОГДА не смешивай со старым
   клиентом `1063227834468-...` или `http://localhost` → это `redirect_uri_mismatch`.

**3a** — Запусти авторизацию (gog сам сгенерирует URL и сохранит code_verifier).
**ВСЕГДА добавляй `--force-consent`**: без него для аккаунта, который УЖЕ давал согласие этому
приложению раньше, Google вернёт только access-токен БЕЗ refresh-токена → gog упадёт с
`no refresh token received`, и подключение не сохранится. `--force-consent` (добавляет
`prompt=consent`) гарантирует refresh-токен. Для первого входа он безвреден (экран согласия и так будет):

```bash
gog auth add <email> --services gmail,calendar,docs,sheets,drive --remote --step 1 --redirect-host social.eightgate.ai --force-consent
```

Из вывода достань URL (начинается с `https://accounts.google.com/...`).
Отправь его пользователю как кликабельную ссылку:

"Открой ссылку, войди в Google и разреши доступ.
После согласия откроется страница EIGHTGATE с кнопкой «Скопировать код».
Нажми её и пришли мне скопированное сюда."

**Жди пока пользователь пришлёт redirect URL. Ничего не запускай в это время.**

**3b** — Обмен кода на токен. Пользователь пришлёт КОД (со страницы с кнопкой
«Скопировать код»); иногда — полный URL. Передай это в gog через `--auth-url`
(те же root-флаги, что и в Шаге 1):

```bash
gog auth add <email> --services gmail,calendar,docs,sheets,drive --remote --step 2 --redirect-host social.eightgate.ai --auth-url "https://social.eightgate.ai/oauth2/callback?code=<КОД>"
# если пользователь прислал ПОЛНЫЙ URL — передай его целиком: --auth-url "<url>"
```

⚠ Код — непрозрачный одноразовый authorization code. Его НЕЛЬЗЯ декодировать
(base64 / JWT / парсинг ссылки) — так токенов не получить. Обмен на токены делает
ТОЛЬКО `gog ... --step 2` (он POST-ит код + client_secret на сервер Google).
НИКОГДА не пиши свой скрипт для разбора/декодирования кода или ссылки.

Проверь:

```bash
gog auth list
```

**3c** — Привязка аккаунта:

Вызови `link_google_account` с email пользователя.
Скажи: "Google подключён."

## Ошибки

- **"Missing code verifier"** — самая частая. PKCE-стан от Шага 1 потерян (сессия
  рестартнула между шагами, ИЛИ Шаг 1 запускали повторно и перетёрли state, ИЛИ
  state-файл подделан вручную). Лечение: начни с Шага 3a ЗАНОВО, пришли НОВУЮ
  ссылку, заверши Шаг 2 сразу. НЕ чини state-файл руками.
- **"no refresh token received; try again with --force-consent"** — аккаунт уже давал согласие
  приложению раньше, поэтому Google не вернул refresh-токен. РЕШЕНИЕ: повтори Шаг 3a с
  `--force-consent` и пришли пользователю НОВУЮ ссылку. (По умолчанию всегда используй
  `--force-consent` — тогда этой ошибки не будет вообще.)
- "invalid state" / "code already used" — код одноразовый, начни с Шага 3a заново
- "invalid_grant: Token has been expired or revoked" — рефреш-токен протух
  (приложение в Testing → токены живут ~7 дней). Переавторизация по Шагу 3.
- "invalid_client" — проблема с OAuth клиентом на сервере, сообщи администратору
- "no TTY available for keyring" — нужен GOG_KEYRING_PASSWORD в окружении

## Важные правила

- НИКОГДА не проси пользователя создавать OAuth client в Google Cloud
- НИКОГДА не проси пользователя скачивать или присылать JSON файл
- НИКОГДА не упоминай gog, OAuth, tokens, JSON, credentials в сообщениях
- НИКОГДА не декодируй/парси код или ссылку вручную (base64/JWT/python). Обмен
  делает только `gog ... --step 2 --auth-url` — код непрозрачный, его не раскодировать
- НИКОГДА не собирай ссылку авторизации руками и не редактируй state-файлы — см. выше
- Говори простым языком: "открой ссылку", "пришли URL", "Google подключён"

- АККАУНТ ДЛЯ ПОДКЛЮЧЕНИЯ — ВСЕГДА собственный email КЛИЕНТА (спроси его). НИКОГДА не используй
  и не называй служебный/системный адрес агента (eightgatecopr@gmail.com) — это внутренний
  Claude-аккаунт платформы, НЕ для клиента и НЕ для входа в Google.
